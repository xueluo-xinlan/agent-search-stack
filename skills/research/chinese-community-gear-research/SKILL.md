# 中文消费电子器材横评调研

## When to Use

- 用户要**横向 / 纵向对比**几款中文市场在售器材（耳机、小尾巴/DAC、键盘、鼠标、显卡、手机等），要求以**官方数据 + 社区真实评价**为准。
- 关键词通常是「官方参数」「B站/贴吧测评」「使用评价」。
- 用户明确说「**不要商单、广告和推送**」时，本技能的来源分级是硬要求，不是可选项。

检索阶梯与各后端可用性见 `web-research-playbook`（用户自有技能，可用则优先参考）；PC 侧通道与脚本投递见 `windows-remote-ssh-admin`。

## 总流程

1. **先建产品清单表**（型号 / 别名 / 品类），一次查全再动笔。中文产品的型号别名差异极大（同一产品有中文名、拉丁名、绰号、配色名），先固定检索词再搜。
2. **官方页拿规格**：优先厂商官网产品页与官博，拿到价格、单元/架构、接口、电声参数。
3. **独立测评拿听感**：B站测量向/自购向 UP、独立博客，取其结论与其**引用的测量数据**。
4. **社区评价拿真实缺陷**：B站评论区 + 贴吧，重点捞「到货体验、退换、吐槽」这类非营销内容。
5. **成表交付**：横评矩阵 + 纵向代际 + 搭配/决策建议 + 来源分级 + 未获取项（见下）。

## 硬要求一：来源四档分级（交付时必须显式写出）

| 档 | 内容 | 用法 |
|---|---|---|
| ① 官方规格 | 官网/官博 | **可直引**（价格、参数、架构） |
| ② 独立测评 | 自购自测、有测量流程的 UP/博客 | 听感与测量的主要依据 |
| ③ 用户评论 | 评论区/贴吧片段 | 可用于「已知缺陷/争议」，须注明是**个体意见** |
| ④ 排除 | 经销商带货号与带货直播、官方账号自评、话术稿（「X 打 Y」式）、标注送测/PR 的稿件 | **其参数可引，听感结论不可采信**；报告中列明排除了哪些 |

- 用户强调「不要商单」时，**在报告里单独列一段「已识别并排除的推广内容」**——这是可验证的交付项，不是客套。
- 送测稿的价值边界：参数可信（厂商给的数据），结论打折（作者拿了样机）。

## 硬要求二：不虚构参数

- **官方未公布的项留空并写明「官方未公布」**，绝不用上代同系列的数据代填（如把上代的阻抗/灵敏度填给新一代）。
- **不同负载（Ω）下标的功率不可直接比大小**；标称口径与实测口径分开列。
- 来源冲突时（官网 vs 媒体表格），以官网为准并注明冲突点。
- 结尾必须有一段「未获取 / 需自行核实」——把拿不到的（某些站点的正文、未公布参数、口径不明的数值）如实列出来。

## B站 数据采集（评论区是社区口碑主力）

**三条判据（缺一不可）**：

1. **IP 决定成败**：`api.bilibili.com` 对 VPS 机房 IP 返回**拦截页 HTML**（不是 4xx，极易被误读成「接口没数据」）→ 脚本投到 **PC 住宅 IP** 上跑。
2. **UA 形状决定 412**：简单 UA（`curl/8.4.0`）**放行**；Chrome UA + `buvid3` cookie → `HTTP Error 412: Precondition Failed`。别为「更像浏览器」补 cookie。
3. **成功判据是响应体形态**：含 `code`/`data` 的 JSON 才算成功；拿到 HTML 一律按「被拦」处置。

**限速与分批（硬约束）**：搜索/评论接口请求间隔 3–4s，一批 4–5 个 URL；单次 SSH 前台调用 ~420s 超时（超时 = 该批输出全丢）→ 分批跑、每批增量落盘再汇总。先探通一个 BV 再批量。

可复制配方（投递、请求形状、落盘）：`references/bilibili-tieba-harvesting.md`。

## 贴吧 正文取不到时的处置

`/f/search` 与 `/p/<id>` 帖子页撞「百度安全验证」时，**先分清是哪种上下文**：

- **全新（零 cookie）上下文** —— curl、headless、**有头**浏览器全一样被甩滑动拼图；与机房/住宅 IP 无关（两端实测逐条一致）。
- **已通过过一次验证的常驻上下文** —— 同一时刻、同一 IP、同一 URL 能读出帖子（实测：MCP `agent_search_gateway` 的 `fetch` 走 PC 常驻渲染层，拿到了帖子标题与正文）。

⇒ 变量是**会话的持久化状态**，不是 headless/headed、也不是 IP。要稳定读贴吧，得让抓取层用 `launch_persistent_context` 复用已过验证的 profile。

仍拿不到时：
- 改用**搜索引擎索引片段**（`site:tieba.baidu.com <关键词>`、`~/exa_search.py`）。
- 常驻实例即便通了，Readability 也可能被站内侧栏（「大家都在逛的吧」）挤占正文 —— **标题对了不等于正文对了**，引用前核正文。
- 报告里**显式标注该来源缺口**，绝不把索引摘要当帖子原文引用。
- 需要一手内容时请用户手动开页面提供（一次问清，别反复要）。

## 多平台批量抓取：MediaCrawler 通道

要一次按关键词抓小红书/B站/贴吧/知乎/微博/抖音/快手，用本机 MediaCrawler（7 平台全支持手机扫码登录，登录态可复用、免二次扫码）。
操作要点、登录窗口脚本、桌面一键 bat 约定，以及用户报「脚本没动」时的取证顺序：`references/mediacrawler-scraping.md`。

## 厂商官网找规格：用列表页/sitemap，别猜 slug

- **状态码不能证明 slug 存在**：营销站（Webflow 一类）对任意路径都返回 200 + 首页内容，拿 200 当「页面存在」会误判。
- 正确入口：站点分类/列表页（如 `…/product-category/dac/`、`…/headphones`）与 `sitemap.xml` / `sitemap_products*.xml`，从里面枚举真实产品 slug。
- 产品页的规格段常带固定前缀（如「产品信息」「商品参数」），按前缀截取比全页读省 token。

## 报告交付规范（用户偏好）

- **结论先行**：开头一段「一句话结论 + 选购速览」，再展开表格。
- **横评矩阵**：每类产品一张表，行是可比较的维度（价格 / 架构 / 官方电声 / 接口 / 玩法 / 调音倾向 / 已知短板 / 适合人群）。短板要写实，不写「仅供参考」。
- **纵向（代际/同门）单独一段**：与上代、与同门更高配的关系，指出价格与定位变化。
- **交叉搭配表**：耳机 × 前端（或器材 × 配件）的推荐与依据，这是用户真正要的决策结论。
- **来源分级 + 未获取项**放最后（见上两条）。
- 桌面端可另出一份 HTML 对比卡片，用 `::preview{file="…"}` 内联（theme 变量上色、不设自带背景/字体）。

## 电商规格取数：尺寸藏在哪一层

要按尺寸选货（如"高 200 / 深 35 / 宽 80"），先知道哪一层才有尺寸：

| 层 | 有尺寸吗 | 实测 |
|---|---|---|
| 淘宝/天猫**列表页** | ❌ | 301 条标题三维尺寸 **0 命中**（只有"1.9 米"这类单维词） |
| 淘宝**详情页** | ✅ | 在 **SKU 名称字符串**里：`80长阳光板书柜(200*80*35cm)`。抓 HTML 后正则 `\d{2,4}[*x×]\d{2,4}[*x×]\d{2,4}` 即可 |
| 苏宁搜索页 | ✅ | 商品名自带 mm：`戴劲…600*400*1600mm`，解析成 `[宽,深,高]` |
| 京东 H5 | 部分 | 元数据免登录可得，**价格是账号墙**（见 blocked-page-recovery） |

- **噪声要按上下文滤**：淘宝详情页每条都含 `24*60*60`（页面模板里 cookie 过期时间的计算式），别把它当规格——取 `商品规格` 附近的命中。
- **数字顺序别猜，看 SKU 名里的"长/宽"**：`(200*80*35cm)` 配 SKU 名"80长"→ 80 是正面宽、35 是深、200 是高。
- **标准现货档位**（多站交叉一致）：宽 40/60/80/100，深 25–40（30/32/35/40），高 160/180/200 cm。**深 55、高 190 这类非标值基本没有现货，只能定制**——先用档位筛，再去站点验证。

## Pitfalls

- **别用「results 条数」或「HTTP 200」判断抓取成功**：判据必须落在响应体形态（JSON 结构）或页面特征串上。
- **评论/测评标题先过推广词过滤**再入库（`加V|加微信|优惠券|领券|进群|代购|闲鱼|关注我|橱窗` 一类），否则商单话术会直接进结论。
- **同一产品的中文名与拉丁名要同时检索**；只搜中文名会漏掉大量测评（UP 常用拉丁名做标题）。
- **配色 / 限定版属于同一型号**：价格与线材可能不同（换线、附赠），对比表里要标出差异，别混为一谈。
- **写「厂商未公布」也是结论**：空白格比一个编造的数字有价值得多。
